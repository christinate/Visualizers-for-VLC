# Immutable source archive preparation

Observed locally on 2026-11-16. This covers source-archive tooling; final
candidate source/binary builds and tags remain D72/D73 work.

## Confirmed problems and changes

Geiss64, MilkDrop2-64, Terrain64 and the Catalog previously wrote their source
ZIP, `RELEASE.json` and `SHA256SUMS.json` directly into the shared releases
directory. A new source release would replace earlier metadata/checksums.
All five source helpers now require a fresh directory, defaulting to
`releases/<VERSION>/source/`. Even an existing empty directory is refused.
`--output PATH` supports another fresh destination. Each archive, release
metadata and checksum file is created exclusively; checksums cover only that
candidate directory. Existing release directories/files are not refreshed.

The Addon already used a fresh directory, but resolved a commit for metadata
and then archived the movable name `HEAD`. A controlled test with the actual
old helper reproduced mismatched provenance: metadata identified a 0.5 source
commit while the ZIP's Git comment and VERSION identified a later 0.6 commit.
The corrected helpers pass one fixed commit ID to `git archive`, read VERSION
and any security policy from that commit, and verify the archived VERSION.

Testing also observed Windows Git settings exporting CRLF where the committed
fixture used LF. The archive command now pins `core.autocrlf=false` and
`core.eol=lf` for that command. UTF-8 console output fixes a second observed
failure: a valid Unicode output path had completed its files but then returned
an error while printing that path through a CP1252 pipe. Source archive
preparation requires Python 3.11+ and Git, as documented in every README.

## Validation

`tools/test_source_release.py` copies each actual helper into an isolated
local Git repository. It invokes real Git/archive commands, verifies ZIP
contents and commit comments, archive/metadata SHA-256 values and byte counts,
and checks preservation of earlier release files. Only the controlled HEAD
change is injected at the subprocess boundary; the archive itself is real.

Each of five helpers passes these nine cases on Windows and Linux:

1. Default source archive preserves earlier metadata, checksums and ZIP bytes.
2. Reusing an output directory refuses and leaves its files unchanged.
3. A custom Unicode/spaced output directory succeeds.
4. An existing empty output directory refuses.
5. Dirty tracked source refuses before creating output.
6. Untracked source refuses before creating output.
7. A security-held candidate refuses before creating output.
8. An invalid committed VERSION refuses before creating output.
9. Concurrent actual HEAD/VERSION changes still archive the fixed earlier
   commit, with matching metadata, Git ZIP comment, VERSION and payload.

Result: **45 cases pass per platform**. Windows uses Git 2.47.1.windows.2;
Mint uses Git 2.43.0 from an Ubuntu package extracted into a private development
tools directory. Its package SHA-256 was checked against local APT metadata;
it is not included in visualizer payloads and no system installation changed.
The initial Linux run lacked Git; it remains separate from the passing run.
